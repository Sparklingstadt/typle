## Release workflow

Read `docs/release-workflow.md` before publishing changes. The required order is
PR → CI (`verify`) → merge (squash by default, ordinary merge when the user asks) → CI on main: policy and verify → GitHub Release → Vercel production deploy → production checks.
Since v2.60.6 GitHub Actions (`ci.yml`) does everything after the merge, so **merging a PR publishes it to production**:
get the user's confirmation before merging, and merge one PR at a time, only after the main run of the previous merge
has finished its deploy. Do not push directly to main. Prepare a PR with a new stable package version. A failure must be
fixed or retried at the failed stage, never bypassed. (`docs-deploy.yml` publishes `api-docs/` on request. From v2.38.1
to v2.60.5 the Release and the deploy were done by hand.)

Every PR takes a version no other commit has used: before `npm version`, check
`git tag` and the GitHub Releases, and bump again if the PR's version was taken
by a PR merged in the meantime.

### Verify

`npm run verify` (`scripts/verify.cjs`) runs every check in this order and stops at the first failure:
`npm run db:migrate` on the local database (`DATABASE_URL` in `.env.local`; the DB tests add rows under random
owners and delete them), `node --test tests/migrate.test.cjs`, `npm run typecheck`, `npm test`, `npm run lint`,
`npm run knip`, `npm run build`, the AWS CDK app's checks in `infra/` (typecheck, tests, synth), `npm run test:e2e`, and `npm run docs:build` / `npm run docs:check` in `api-docs/`. `npm run verify -- --fast` leaves out the end-to-end tests and the API docs while
working; run it in full before opening the PR. It needs Docker (the local PostgreSQL) and Node.js 24, so a
cloud session cannot run it: say so and hand it to the user. The CI runs the same command on Linux, where the
screenshot snapshots (`tests/e2e/screenshots.spec.ts`, macOS only) are skipped: the run on the Mac before the PR is the
only one that compares them, and nothing after the merge does.

### Merge, release and deploy (CI)

1. Merge only when the PR's `verify` has passed and the user has confirmed. Give the squash or merge commit the PR's
   title with its `(vX.Y.Z)`: `gh pr merge <number> --squash --subject "<PR title> (#<number>)"` (GitHub would take a
   one-commit PR's commit title instead, which has no version).
2. The CI run of the main commit then does, in order: `policy` (the push is one merged PR's commit) and `verify`;
   `credentials` (the Vercel token still signs in); `release` (the GitHub Release `v<package.json version>` on that
   commit, non-draft, non-prerelease, notes generated by GitHub; a tag is never moved and a version never reused);
   `deploy` (`vercel deploy --prod` of that commit, a wait until the production domain serves it, then
   `scripts/check-production.cjs`, which checks `https://typle.sparklingstadt.com` (including the Auth.js sign-in) and
   the Vercel domain `https://typle-r-six.vercel.app`).
3. Read the run's result (the ccd_pr tools or `gh run list --branch main --workflow CI --limit 1`, once, not in a loop)
   and tell the user. When a job failed, read its log: a cause outside the code (the token, a network error) is fixed
   and the failed jobs are run again; a cause in the code needs a new PR with a new version.
4. When `api-docs/` changed, run the "Docs deploy" workflow on main (`docs-deploy.yml`).

Only when Actions cannot publish (it is down or unpaid), publish by hand on the user's Mac, after the user confirms
each step: `git switch main && git pull --ff-only`, `npm run verify` in full, the Release
(`gh release create "v$(node -p "require('./package.json').version")" --target "$(git rev-parse HEAD)" --title "v$(node -p "require('./package.json').version")" --generate-notes --latest`),
`vercel deploy --prod --yes` from the same checkout, and `npm run check:production` once the production domain serves
the new deployment.

## コードとコミットの規約

- `src` のディレクトリーは README の「コードの構成」にあります。`eslint.config.mjs` が
  画面から保存先（`src/lib/storage`）とサーバーのコード（`src/server`）への import をエラーにします。
- squash merge・普通のマージのコミットのタイトルと PR のタイトルは、変更を日本語の1文で書き、末尾に半角の
  `(vX.Y.Z)` を付けます。`fix:` などの接頭辞は付けません。PR 番号は squash merge で付き、普通のマージでは手で付けます。コミットが1つだけの PR を GitHub の画面で squash すると、PR のタイトルではなくコミットのタイトルが入るので、マージのときにタイトルを指定します。PR の途中のコミットは内容だけを書き、`(vX.Y.Z)` は付けません。

## 出力の言語

ユーザーへの返答、PR のタイトル・説明、コミットメッセージ、`docs/`・README・CHANGELOG は日本語で書くこと。
コードのコメントと識別子、`CLAUDE.md` の Release workflow の節のように英語で書かれている箇所は、
周りに合わせて英語で書く。
